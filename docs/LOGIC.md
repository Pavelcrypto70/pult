# Пульт · логика продукта и пользователя

Документ описывает **полную логику** салона дверей и ведётся во время разработки.  
Фокус: канбан сделок, блоки, карточки, переходы, конструктор полей, задачи шефа, **диалоги Max как у Битрикса** (§8).

---

## 1. Продукт в одном предложении

**Пульт** — операционка магазина дверей: три направления сделок на канбане, карточки заказа с богатым шаблоном полей, автоматический и ручной перенос между блоками, задачи команды и обзор по салону.

Не делаем: конструктор компаний, multi-tenant CRM «на всё», отдельный модуль клиентов в меню (клиент живёт внутри карточки сделки).

---

## 2. Роли пользователей

| Роль | Кто | Что может |
|---|---|---|
| **Шеф (владелец)** | Анна и аналоги | Все направления, настройка блоков, конструктор шаблона карточки, назначение задач любому, отчёты/обзор, админка команды |
| **Менеджер** | Продажи / сопровождение | Свои и командные сделки в разрешённых направлениях, создание карточек, drag карточек, задачи себе и подчинённым (если выдано) |
| **Оператор направления** | Ксения, Катя и т.п. | Работа в «своих» блоках (обработка, рекламации), заполнение полей, переход дальше по действию |
| **Монтаж / сервис** | Бригада, сервис | Карточки в монтажных/гарантийных блоках, вложения, статусы выезда |
| **Админ** | Технический | Команда, роли, интеграции (Telegram / Max / почта) |

Правило видимости блоков: шеф видит всё; остальные — направления и блоки по правам (позже RBAC; в демо — всё открыто).

---

## 3. Карта экранов (текущий контур)

| Экран | Назначение |
|---|---|
| **Обзор** | Сводка: суммы по направлениям, флаги, нагрузка, операционные сигналы |
| **Сделки** | Канбан: 3 направления → блоки → карточки |
| **Задачи** | Вид шефа: выбор человека + создание задачи (суть, документы, исполнитель) |
| **Витрина / Заказы / Замеры / Монтаж** | Салонные экраны (каталог и сервис); конфигуратор временно скрыт |
| **Админка** | Команда, роли, интеграции |

Связь: карточка сделки — **центр правды**. Витрина/замеры/монтаж дают сущности, на которые карточка ссылается (дверь, замер, слот).

## 4. Три направления (верхнее меню канбана)

Переключатель направлений (как сейчас в UI):

1. **Продажа** — от заявки до передачи в производство  
2. **Поставка / Доставка / Монтаж** — исполнение заказа (столбцы как на скрине)  
3. **Пост гарантийный сервис** — обращения после сдачи  

У каждого направления:
- свой **набор блоков** (столбцов);
- свой **порядок блоков** (editable, drag);
- свой **шаблон карточки** (какие поля обязательны / видны) — может наследоваться от общего шаблона салона с оверрайдами.

При смене направления канбан полностью переключается: другие блоки и другие карточки.

### 4.1. Стартовый набор блоков «Поставка / Доставка / Монтаж» (эталон со скрина)

| # | Блок | Смысл |
|---|---|---|
| 1 | Не отправленные в работу | Новые / ещё не взятые в операционный контур |
| 2 | В обработке у Ксении | Внутренняя обработка (персонализированный блок) |
| 3 | Заявка у поставщика | Ждём поставщика |
| 4 | Рек в обработке у Кати | Рекламация внутри |
| 5 | Рекламация у поставщика | Рекламация снаружи |
| 6 | Требует доработки менеджера | Возврат на менеджера |
| 7 | Заказ в работе | Основной поток исполнения |
| 8 | Рекламация в работе | Рекламация в работе у нас |

Блоки **персональные** («у Ксении», «у Кати») — это обычные блоки с меткой `assigneeHint` / цветом; не отдельная сущность пользователя. Переименование и порядок — в настройках направления.

Продажа и Сервис имеют свои стартовые наборы (как в демо-данных), редактируемые тем же конструктором.

## 5. Сущности

### 5.1. Направление (`Direction`)
- `id`, `title`, `order`
- список `blockIds`
- ссылка на `cardTemplateId` (или override полей)

### 5.2. Блок (`Block` / столбец)
- `id`, `directionId`
- `title`, `color`, `order`
- `wipLimit` (опционально)
- `isTerminal` — финальный (например «Закрыто»): автопереход дальше не идёт
- `allowedActions[]` — какие действия с карточки доступны в этом блоке
- `onActionSuccess` — правило: «после действия X → блок Y» (см. §7)

Шапка блока (UI как на скрине):
- название
- счётчик карточек
- сумма ₽ по карточкам блока

### 5.3. Карточка сделки (`DealCard`)
Минимальный паспорт + поля из шаблона.

Базовые поля всегда:
- `number` (546-2026)
- `directionId`, `blockId`
- `amount`
- `createdAt`, `updatedAt`
- `createdBy`, `flags[]` (просрочена, просмотрена, …)

### 5.4. Шаблон карточки (`CardTemplate`) — конструктор

При **создании / редактировании блоков и направления** шеф собирает, **что можно ставить в карточку** (как конструктор полей). Это не отдельный «Битрикс-комбайн», а чеклист модулей полей:

| Модуль поля | Что хранит | Зачем |
|---|---|---|
| **Текст / суть** | rich/plain text | Описание, комментарий оператора |
| **Документы** | файлы (КП, фото, акты, схемы) | Вложения к заказу |
| **Ответственные** | 1+ сотрудников + роль на карточке | Кто ведёт, кто монтаж |
| **Контакты** | ФИО, телефон, мессенджер | Клиент / прораб / дизайн |
| **Замеры** | ссылка на замер(ы) + краткие размеры | Связь с модулем замеров |
| **Ссылка на дверь** | модель / SKU / конфигурация с витрины | Что продаём/ставим |
| **Сроки** | крайняя дата поставки, монтажа, внутренние дедлайны | Просрочки и флаги |
| **Ссылка на чат в Max** | URL / deep-link чата Max | Быстрый переход в переписку |
| *(позже)* Сумма / предоплата, производитель, вид работ, кол-во проёмов | уже есть в демо-карточках | Деньги и спецификация |

В конструкторе для каждого модуля:
- вкл/выкл на направлении;
- обязательность при создании / при выходе из блока;
- порядок на карточке;
- кто видит / кто редактирует (шеф / менеджер / оператор).

### 5.5. Задача (`Task`) — отдельно от карточки сделки

Задачи шефа **не заменяют** канбан, а обслуживают людей:
- название, **суть** (текст), **документы**
- исполнитель, приоритет, статус, срок
- опционально: `linkedDealCardId` (задача привязана к сделке)

Создание задачи ≠ создание карточки сделки.  
Но из карточки можно «Создать задачу» с автопривязкой.

## 6. Пользовательские сценарии

### 6.1. Шеф открывает «Сделки»
1. Видит переключатель направлений.  
2. Выбирает, например, «Поставка / Доставка / Монтаж».  
3. Видит горизонтальный ряд блоков (цветные шапки + суммы).  
4. Внутри блоков — карточки.  
5. Может:
   - создать карточку;
   - перетащить карточку;
   - открыть карточку и выполнить действие → автопереход;
   - перетащить блоки местами;
   - открыть настройки блоков / конструктор шаблона (в т.ч. правила Max §8).

### 6.2. Создание карточки
1. «+ Создать» / «+ Быстрая сделка».  
2. Форма:
   - выбор **направления** (по умолчанию текущее);
   - выбор **блока**, куда положить карточку (обязательно; по умолчанию — первый блок направления или «Не отправленные в работу»);
   - поля по шаблону: суть, контакты, ответственные, дверь, сроки, Max (URL и/или привязка диалога), документы…  
3. Сохранение → карточка появляется в выбранном блоке.  
4. В ленте обзора — событие «Создана сделка …».

### 6.3. Работа внутри карточки (действие → следующий блок)
1. Пользователь открывает карточку.  
2. В текущем блоке доступен набор **действий** (кнопки), например:
   - «Отправить Ксении»
   - «Отправить поставщику»
   - «Вернуть менеджеру»
   - «Взять в работу»
   - «Закрыть рекламацию»
3. При успешном действии (и если обязательные поля блока заполнены):
   - карточка **автоматически** переезжает в целевой блок по правилу;
   - пишется история: кто, когда, из какого блока в какой, какое действие;
   - обновляются флаги (например, снимается «Просмотрена», ставится новый срок);
   - если у действия / целевого блока включён Max (§8) — ставится исходящее в диалог клиента.

Если обязательные поля не заполнены — действие блокируется с подсветкой недостающего (документы / замер / Max и т.д.).

### 6.4. Ручной перенос карточки (drag-and-drop)
1. Пользователь берёт карточку **за край / хендл** и тащит в другой блок.  
2. Drop разрешён, если:
   - целевой блок того же направления;
   - роль позволяет (шеф — всегда; менеджер — по правам);
   - нет жёсткого запрета «только через действие» (флаг блока `strictFlow`, опционально).  
3. После drop:
   - `blockId` меняется;
   - в истории: «Перенесено вручную …»;
   - если в целевом блоке есть обязательные поля — карточка помечается флагом «Требует заполнения», но не откатывается (чтобы не ломать UX); строгий режим можно включить позже;
   - Max по `manual_drop` по умолчанию **выключен** (включается явно в конструкторе).

Автопереход и ручной перенос **сосуществуют**: авто — основной сценарный путь; drag — исключение и гибкость «как в Битриксе».

### 6.5. Перетаскивание блоков
1. Шеф в режиме настройки (или сразу на доске за шапку блока) тащит блок горизонтально.  
2. Меняется `order` блоков направления.  
3. Карточки остаются в своих `blockId`; меняется только визуальный порядок столбцов.  
4. Суммы и счётчики пересчитываются от содержимого, не от позиции.

### 6.6. Создание / редактирование блока + большой конструктор
1. «+ Блок» или «Настроить направление».  
2. Параметры блока: название, цвет, лимит WIP, персональная метка, strictFlow, **правила Max** (вкл, когда слать, шаблон).  
3. **Конструктор содержимого карточек** (шаблон направления):
   - список модулей полей (текст, документы, ответственные, контакты, замеры, дверь, сроки, Max-чат, …);
   - для каждого: вкл, обязательность, порядок, подпись;
   - превью карточки справа.  
4. Правила переходов: таблица «Действие → целевой блок» (+ опционально notify Max).  
5. Сохранение → доска обновляется без перезагрузки смысла данных.

### 6.7. Задачи шефа
1. Шеф выбирает сотрудника (включая себя).  
2. Видит его задачи.  
3. «Новая задача»: название, **суть**, документы, исполнитель, приоритет, статус, срок, опционально сделка.  
4. Исполнитель в будущем видит «Мои задачи»; сейчас в демо — тот же экран фильтрацией.

### 6.8. Клиент получает сообщение в Max при смене блока
1. У сделки уже есть `dialog.status = linked` (клиент писал / чат привязан).  
2. Срабатывает действие или вход в блок с `notifyMax`.  
3. Пульт (через бэкенд/коннектор) отправляет шаблон в **личный диалог**.  
4. В карточке — запись истории «Max: доставлено» или «не доставлено».  
5. Если диалога нет — задача менеджеру «привязать чат», клиенту ничего не уходит.

## 7. Логика переходов между блоками

### 7.1. Два механизма

| Механизм | Когда | Как |
|---|---|---|
| **По действию** | Нажали кнопку действия в карточке | `actionId` → `targetBlockId` |
| **Вручную** | Drag карточки | Пользователь выбрал целевой блок |

### 7.2. Пример матрицы для «Поставка…» (черновик правил)

| Из блока | Действие | В блок |
|---|---|---|
| Не отправленные в работу | Взять в обработку (Ксения) | В обработке у Ксении |
| В обработке у Ксении | Отправить поставщику | Заявка у поставщика |
| В обработке у Ксении | Нужна доработка менеджера | Требует доработки менеджера |
| Заявка у поставщика | Поставщик подтвердил / в работу | Заказ в работе |
| Заявка у поставщика | Открыть рекламацию | Рекламация у поставщика |
| Рекламация у поставщика | Передать Кате | Рек в обработке у Кати |
| Рек в обработке у Кати | Вернуть поставщику | Рекламация у поставщика |
| Рек в обработке у Кати | В работу по рекламации | Рекламация в работе |
| Требует доработки менеджера | Исправлено, снова в поток | Не отправленные / к Ксении (настраивается) |
| Заказ в работе | Открыть рекламацию | Рекламация в работе |
| Рекламация в работе | Закрыть рекламацию | Заказ в работе (или терминальный «Готово») |

Правила хранятся данными, не хардкодом UI — чтобы шеф менял их в конструкторе.

### 7.3. Цепочка «после любых действий — следующий блок»

Под «действием» понимаем не только смену блока, а **завершённый осмысленный шаг**:
- отправили поставщику;
- приложили акт;
- проставили срок монтажа;
- связали замер;
- нажали «Готово по шагу».

Каждый такой шаг может:
1. сохранить поля карточки;
2. создать событие в истории;
3. **сдвинуть карточку** в следующий блок по правилу;
4. опционально создать задачу ответственному следующего блока;
5. опционально дернуть интеграцию (уведомление в Max).

## 8. Max и внешние связи (диалог как в Битриксе)

### 8.1. Цель

Клиент получает сообщение **в своём личном диалоге с салоном** (не пост в канале бота), когда сделка попадает в определённый блок или выполняется действие.  
Модель — как у Битрикса: **сделка → привязанный диалог → робот/правило → коннектор → мессенджер**.

### 8.2. Слои (обязательная архитектура)

```
[Канбан / действие / drag]
        ↓
[Правило уведомления на блоке или TransitionRule]
        ↓
[DealCard.dialog  — сессия чата]
        ↓
[Коннектор / бэкенд Пульта]  ← здесь секрет токена
        ↓
[Max API / партнёрский коннектор]
        ↓
[Личный диалог клиента в Max]
```

Без слоя **Dialog у карточки** автоматика «как в Битриксе» невозможна: одной ссылки `maxChatUrl` недостаточно для API-отправки.

### 8.3. Сущность Dialog (на карточке сделки)

У `DealCard` хранится привязка к диалогу (один активный на канал; позже — массив):

| Поле | Смысл |
|---|---|
| `channel` | `max` (позже whatsapp / telegram) |
| `status` | `unlinked` · `pending` · `linked` · `blocked` · `error` |
| `maxUserId` | ID пользователя Max (для Bot API `user_id`) |
| `externalChatId` | ID диалога у коннектора (если не чистый Bot API) |
| `maxChatUrl` | deep-link «открыть чат» для менеджера (как сейчас) |
| `phone` | телефон контакта (для коннекторов «написать первым») |
| `lastOutboundAt` | последняя исходящая |
| `lastInboundAt` | последнее входящее |
| `lastError` | текст ошибки доставки |

**Статусы:**
- `unlinked` — нет привязки; автосообщения не шлём.
- `pending` — ждём, пока клиент напишет боту / коннектор подтвердит чат.
- `linked` — можно слать в диалог.
- `blocked` / `error` — не слать; флаг на карточке + задача менеджеру.

### 8.4. Как диалог появляется (три способа)

1. **Клиент написал первым** боту / на номер салона → webhook → ищем сделку по телефону / коду заказа → `status = linked`, пишем `maxUserId`.  
2. **Менеджер открыл чат из карточки** (кнопка Max) и переписка уже шла — ручная или полуавто привязка.  
3. **«Написать первым»** через коннектор по телефону (если канал и тариф позволяют) → создаётся сессия → `linked`.

Пока диалог `unlinked` / `pending` — правило Max **не молча глотает** событие: пишет в историю «не отправлено: нет диалога» и опционально создаёт задачу.

### 8.5. Правило уведомления (на блоке или на действии)

В конструкторе направления у блока / у `TransitionRule`:

| Поле | Смысл |
|---|---|
| `notifyMax` | вкл / выкл |
| `notifyOn` | `enter_block` · `action_success` · `manual_drop` |
| `templateId` / `templateText` | текст с плейсхолдерами |
| `skipIfUnlinked` | `true` = только лог; `false` = ещё и задача менеджеру |
| `oncePerCard` | не слать повторно при повторном входе в тот же блок |

**Рекомендация салона:** триггерить на **`action_success`** (осмысленный шаг: «Отправить поставщику»), а не на любой ручной drag — меньше случайных сообщений клиенту.  
`enter_block` — для стабильных операционных статусов («Заказ в работе»).  
`manual_drop` — по умолчанию **выкл**.

### 8.6. Плейсхолдеры шаблона

- `{number}` — номер сделки  
- `{client}` — имя клиента  
- `{block}` — название блока  
- `{deadline}` — срок поставки  
- `{door}` — SKU / модель  
- `{owner}` — ответственный  

Пример:  
«Здравствуйте, {client}! Заказ {number} передан поставщику. Ориентир поставки: {deadline}. Салон Première.»

### 8.7. Сценарий «робот как в Битриксе»

1. Менеджер нажимает действие «Отправить поставщику» (или карточка входит в блок с `notifyOn = enter_block`).  
2. Проверяются обязательные поля выхода / checklist действия.  
3. Карточка переезжает в целевой блок, пишется история перехода.  
4. Движок смотрит правило Max целевого блока (или самого действия).  
5. Если `dialog.status === linked` → коннектор/бэкенд шлёт текст в Max.  
6. В `history` карточки: `kind: "notify"`, канал, шаблон, `delivered` / `failed`.  
7. Если нет диалога → `failed` + опционально задача «Привязать Max и отправить вручную».

Клиент видит сообщение **в том же личном диалоге**, где общался с салоном.  
Менеджер в Пульте видит факт отправки в истории карточки (полный двусторонний inbox — этап 2+).

### 8.8. Что нужно со стороны Max (прод)

1. Верифицированный **ИП / юрлицо** в MAX для бизнеса.  
2. **Чат-бот** салона (или партнёрский коннектор: Umnico и аналоги).  
3. **Токен** только на бэкенде (не в GitHub Pages / не в `localStorage`).  
4. Клиент хотя бы раз инициировал диалог с ботом **или** коннектор умеет писать первым по правилам канала.  
5. TLS / сертификаты по требованиям Max API (`platform-api2.max.ru`).

Чистый Bot API Max ≠ пост в канале: `POST /messages?user_id=…` уходит в **личный диалог** с ботом.  
Если нужен диалог «как с номером салона» без ощущения бота — обычно берут **коннектор**, как Wazzup/Umnico у Битрикса.

### 8.9. Этапы внедрения в Пульте

| Этап | Что |
|---|---|
| **A · Логика + UI (сейчас в доке)** | поля Dialog, правила на блоке, шаблоны, запись в историю |
| **B · Mock** | при срабатывании правила — «сообщение поставлено в очередь (демо)», без токена |
| **C · Бэкенд** | endpoint `POST /api/notify/max`, секрет токена, реальная отправка |
| **D · Inbox** | входящие из Max в карточку / общую линию (полноценные «открытые линии») |

Статический демо-сайт без бэкенда остаётся на этапе **B**.

### 8.10. Прочие внешние ссылки

- Дверь: `doorRef` / SKU → витрина.  
- Замер: `measurementRef` → экран замеров.  
- Монтаж: `installJobId` → слоты монтажа.  
- `maxChatUrl` остаётся кнопкой «Открыть чат» для человека; API-отправка идёт через Dialog.

## 9. Флаги и суммы

Флаги карточки (демо и прод):
- Просрочена (срок < сегодня и блок не терминальный)
- Просмотрена
- Изменён крайний срок
- Поля заполнены
- Срочно
- Требует заполнения (после ручного переноса в блок с обязательными полями)
- **Max не доставлен** (`max_undelivered`) — правило сработало, диалога нет или API вернул ошибку

Сумма в шапке блока = Σ `amount` карточек в блоке.  
Сумма направления = Σ по всем блокам направления.

## 11. Состояния и ошибки (UX)

- Пустой блок — плейсхолдер «Пусто» + «+ Быстрая сделка».  
- Drop в запрещённый блок — подсветка красным, карточка возвращается.  
- Действие без обязательных полей — модалка «Заполните: …».  
- Конфликт двух вкладок (редко в MVP) — last-write-wins + toast.  
- Файл в документах: в MVP храним метаданные + local/demo; загрузка на бэкенд — этап 2.  
- Max: нет диалога → toast/баннер «Нет привязанного чата» + история `failed`; API error → флаг `max_undelivered`, можно «Повторить».  
- Max mock (этап B) → в истории явно: «Демо: сообщение не ушло в Max (нет бэкенда)».

## 14. Принципы, которые не ломаем

1. Продукт = **магазин дверей**, не универсальный Битрикс.  
2. Канбан направления — главный рабочий стол.  
3. Автопуть и ручной drag оба нужны.  
4. Конструктор — про **поля карточки и правила блоков**, не про создание «компаний».  
5. Визуал — стиль Пульта (не фиолетовый клон Битрикса), шапки блоков — цветные, как на эталонном скрине.  
6. Сначала ясная логика в этом файле → потом код.  
7. Max — **диалог клиента**, привязанный к сделке; токены только на сервере.

## 15. Зафиксированные решения

1. Персональные блоки («у Ксении») — **переименовываемые вручную** (`assigneeHint` + title).  
2. Ручной drag в блок с обязательными полями → **флаг `needs_fill`**, не жёсткий запрет (`strictFlow` — опциональный запрет).  
3. Продажа → поставка: **одна сущность**, смена `directionId` + `blockId`, история сохраняется.  
4. Max:  
   - UI-кнопка: `maxChatUrl` (deep-link);  
   - автоотправка: сущность **Dialog** + правила на блоке/действии (§8);  
   - предпочитаемый триггер: **`action_success`**, не любой drag;  
   - без `linked` диалога — не шлём, пишем `failed` в историю;  
   - прод только через бэкенд/коннектор после верификации ИП в MAX для бизнеса.

## 16. Сводка логики Max «как в Битриксе» (для команды)

**Не делаем:** рассылку в канал бота, хранение токена в браузере, автосообщения без привязки к сделке.

**Делаем:**
1. У сделки есть **диалог** (статус + id).  
2. У блока/действия — **правило** (когда слать + текст).  
3. Событие канбана → проверка диалога → outbox → Max.  
4. Всё фиксируется в **истории карточки**.  
5. Сначала mock, потом живой API.

Аналог Битрикса по ролям слоёв:  
канбан ≈ стадии CRM · правило блока ≈ робот · Dialog ≈ сессия открытой линии · бэкенд/Umnico ≈ коннектор.
